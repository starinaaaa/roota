# Robokassa: тестирование и запуск

Оплата открывается официальным iframe-скриптом Robokassa. Запасная кнопка отправляет ту же подписанную форму методом POST. Node SDK `@robokassa/sdk` закреплён на 1.0.0 и импортируется только сервером.

## Переменные Vercel

Для ветки `codex/robokassa-payments`, только Preview:

- `ROBOKASSA_MODE=test`
- `ROBOKASSA_MERCHANT_LOGIN=roota` (латиница)
- `ROBOKASSA_HASH_ALGORITHM=md5`
- `ROBOKASSA_TEST_PASSWORD1`, `ROBOKASSA_TEST_PASSWORD2`: значения из тестового раздела кабинета, тип Sensitive. Не использовать основные пароли.
- `PAYMENT_BASE_URL`: фиксированный URL preview. Если отсутствует, используется `VERCEL_BRANCH_URL`.

Пароли добавлять непосредственно в Vercel → Project → Settings → Environment Variables; не вставлять их в PR, команды терминала, переписку или `NEXT_PUBLIC_*`. После смены секретов нужен новый деплой. Production-пароли для тестов не требуются, пароль №3 не используется.

`ROBOKASSA_MODE` по умолчанию отключён: обычное оформление заказа продолжает работать. Production публикуется только после отдельного одобрения. Для рабочего режима дополнительно нужны `ROBOKASSA_MODE=live`, `ROBOKASSA_LIVE_ENABLED=true`, `ROBOKASSA_SMZ_READY=true`, основные `ROBOKASSA_PASSWORD1/2` и согласованный `ROBOKASSA_RECEIPT_PROFILE`. Live блокируется в Preview.

## URL и методы

В тестовом кабинете заменить домен на фиксированный preview-домен:

- ResultURL: `https://roota-git-codex-robokassa-payments-starinaaaas-projects.vercel.app/api/payments/robokassa/result`, **POST**.
- SuccessURL: `https://roota-git-codex-robokassa-payments-starinaaaas-projects.vercel.app/payment/success`, **GET**.
- FailURL: `https://roota-git-codex-robokassa-payments-starinaaaas-projects.vercel.app/payment/fail`, **GET**.

После разрешённого запуска домен: `https://roota-liart.vercel.app`. MD5 должен совпадать в тестовом и рабочем разделах кабинета. Для конкретного preview-адреса этой ветки создано исключение Vercel Authentication; остальные preview сохраняют защиту. Проверен публичный доступ к ResultURL.

Success/Fail альтернативные URL тоже подписываются в форме и ведут в окружение, где создан платёж. ResultURL берётся из кабинета. Проверить, что настройки кабинета сохранены, а не только введены.

## Чеки для НПД

Нужен активированный магазин и подключённые **Робочеки СМЗ**, с разрешением интеграции в «Моём налоге». Платёжная квитанция не заменяет чек НПД.

До согласования тестируем оплату без `Receipt`; рабочий режим без согласованного профиля заблокирован. `ROBOKASSA_RECEIPT_PROFILE` — JSON с полями `goods`, `delivery`, `insurance`; у каждого обязательны согласованные `tax`, `payment_method`, `payment_object`. Необязательное `sno` передаётся только если подтверждено для выбранной схемы. Никакие налоговые значения не назначены автоматически.

Согласовать продажу только физлицам либо также ИП/организациям, номенклатуру товаров собственного производства и отражение доставки/страховки. Для B2B до запуска потребуется отдельный сбор реквизитов и подтверждение поддержки схемой СМЗ. Проверить фактическую регистрацию и получение чека НПД перед запуском; тестовая успешная оплата этого не подтверждает.

## Хранение и безопасность

Миграция `20261006130211_robokassa_payments.sql` добавляет `payments` и `payment_test_orders`. Тестовые заказы не создают клиентов, рабочие заказы, резервы, отправки, события и уведомления; корзина сохраняется. Цены, доставка и страховка сверяются с текущим каталогом и серверным расчётом Ozon. Каждая покупка привязана к `cart_session` и ключу идемпотентности. Покупательская Supabase Auth-регистрация не вводится.

Для live применяется существующий транзакционный checkout. ResultURL проверяет подпись с соответствующим Паролем №2, неизменённую строку суммы для подписи, сумму в копейках, `InvId`, подписанные `Shp_payment`/`Shp_mode`. Если присутствует `IsTest`, он тоже сверяется; полагаться только на него нельзя. SQL проверяет связь с заказом и атомарно сохраняет оплату и одно событие. Ошибка БД → 503 без `OK`; повтор после сохранения → `OK{InvId}` без повторного действия. Уведомление не создаёт повторных резервов и не отправляет посылку. После сохранения live-оплаты запускается существующее уведомление студии через outbox; повторное уведомление Robokassa не создаёт повторного сообщения.

Внешний FailURL не меняет базу. Возврат до ResultURL показывает ожидание и опрашивает сервер. Статус и форма доступны только с cookie исходной сессии; чужая сессия получает 404. RLS и запреты EXECUTE закрывают платежи от anon/authenticated. Robokassa-статусы нельзя вручную менять через админку; возвраты пока выполняются в кабинете, синхронизация возвратов требует отдельной реализации. Полученная оплата отменённого заказа фиксируется с событием для ручной проверки, не восстанавливает заказ и его резерв.

## Проверки

`npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`. SQL-тесты проверяют rollback, повтор, неверную сумму/режим, тестовую изоляцию и запреты RLS/RPC. Тесты SDK проверяют неверную подпись, связывание платежа, режим, шесть знаков суммы и дубли параметров.

На preview пройти оформление, iframe, запасной POST-переход, успех, отказ, закрытие окна, ранний возврат, повтор ResultURL и чужую cookie. До ручной проверки настоящего тестового callback, чеков и отдельного разрешения production не запускать.

## Проверенный preview

https://roota-git-codex-robokassa-payments-starinaaaas-projects.vercel.app

На preview проверены HTTP 400 для неверной подписи/суммы/режима, два одновременных подписанных callback и повтор с ответом OK, чтение paid из базы, 404 для чужой сессии, ожидание на раннем SuccessURL, отказ на FailURL и сохранение paid при последующем FailURL. Эти callback отправлены тестовым скриптом; настоящую доставку ResultURL от Robokassa ещё нужно проверить после сохранения preview-адресов в кабинете. Iframe открыл демоформу rootа.

В security advisor новые таблицы отмечены INFO «RLS without policies»: это намеренно закрытый серверный доступ, подтверждены запреты SELECT/UPDATE/EXECUTE для anon и authenticated. Существующие предупреждения о старых функциях и Supabase Auth не относятся к добавленной оплате.
