# Отслеживание, возвраты, раздельная отправка и адресные подсказки

Выпуск 29.10.2026, подготовлен поверх актуальной опубликованной `main` (`bafb469`). Миграции применены с согласия владельца; существующие заказы и оплаченные суммы сохранены. Контрольные реальные отправления, оплаты и возвраты денег не создавались. Тесты используют изолированную PGlite и подставные API Ozon.

## Что изменено

- Для каждой коробки сохраняются актуальная и первоначальная даты доставки, срок хранения, история статусов с датами. Даты показаны по Москве, без обещания точного часа вручения. История повторно загружается после сбоя и при отставании от текущего статуса; один общий неизменный статус больше не препятствует истории другой коробки. Есть лимит запросов истории на запуск. Последняя достоверная история сохраняется при ошибке.
- Покупатель и администратор видят даты и раскрываемую историю каждой коробки. Для ещё не созданной части раздельного предзаказа — «Ожидает изготовления».
- В админке появился раздел `/admin/returns`: отдельно заявки покупателей и отдельно обратные посылки Ozon. Заявки и проблемные возвраты также выводятся на странице «Требует внимания». Обратные посылки привязаны к заказу, включая архивные номера заменённых отправлений; при неоднозначной привязке заказ не подставляется по догадке.
- Ozon-возвраты читаются через `return/search`, история — через `return/status-history`. Используется существующее cron-задание каждые 15 минут, полный проход возвратов обычно раз в час. Есть аренда, курсор, ограничение объёма и времени, повтор после сбоя. Сбой не стирает известные возвраты. Местоположение показывается как последний объект Ozon, не как GPS.
- Получивший оплаченный заказ (либо хотя бы одну посылку раздельного заказа) покупатель может подать заявку на возврат по персональной странице заказа: причина, описание, до трёх фото. Для повреждения/другого изделия требуется фото; если его загрузить нельзя, предусмотрено обращение в студию. Только одна незавершённая заявка на заказ, до трёх обращений за 30 дней; повторное обсуждение можно продолжить со студией.
- Студия меняет статус заявки и пишет ответ, доступный на странице заказа. Это **не** вызов возврата денег и **не** создание обратной доставки. Существующий ручной финансовый возврат остаётся отдельным действием.
- Фото перекодируются в JPEG без исходных метаданных, ограничены по весу/пикселям. Они хранятся в приватном S3-префиксе `return-photos`, ссылки генерируются только в админке и действуют 15 минут. Покупательские файлы не публикуются через публичный оптимизатор изображений. При неоднозначном результате записи БД фото не удаляются; возможные несвязанные объекты следует убирать только после сверки ссылок с БД.

## Расчёт упаковки

По указанию владельца **новые расчёты** включают 250 ₽ **за каждую физическую посылку**:

`доставка = сумма тарифов Ozon по коробкам + сумма страховки + 250 ₽ × количество коробок`.

Четыре тарелки при правиле «по две в коробке» — две коробки, 500 ₽ упаковки. Раздельная отправка готового товара и предзаказа тоже оплачивает упаковку каждой коробки. Сохранённое `delivery_packaging_fee` — итог по заказу, а `delivery_packaging_fee_per_parcel` — 250 ₽. Старые оплаченные снимки не пересчитываются, создание отправления вычитает именно сохранённую плату из оплаченной цены при сверке тарифа Ozon.

Пример со скриншота (сад 3900 ₽ + тарелка 6000 ₽): безопасное чтение существующего расчёта подтвердило две коробки — 1100 г, 150×150×150 мм и 600 г, 265×255×65 мм. Старый расчёт: перевозка 237 ₽ + страховка 59 ₽ + упаковка 250 ₽ = 546 ₽. При новой упаковочной политике и тех же тарифах: 237 + 59 + 500 = **796 ₽**, общий итог **10 696 ₽**. Новый живой расчёт может отличаться; особенно при плановой дате передачи предзаказа в будущем.

## Раздельная отправка

В смешанной корзине Ozon (наличие + предзаказ) появилась галочка «Хочу получить посылки раздельно быстрее». Она сохраняется в черновике, сбрасывает прежнюю цену и инициирует новый расчёт выбранного ПВЗ.

При выборе галочки план упаковки строится отдельно для наличия и предзаказа. Тарелки из разных этапов не объединяются в одну коробку. Каждая коробка получает группу `stock` или `preorder`; при расчёте передаётся собственная плановая дата сдачи, для предзаказа учитывается срок изготовления. Цена и состав фиксируются в серверном расчёте; SQL проверяет совпадение галочки и плана. Оплата остаётся одной за Roota-заказ.

В админке кнопка «Создать следующую готовую отправку Ozon» сначала создаёт только коробки из наличия. Второй этап создаётся после отметки `ready` у всех производственных задач предзаказа. Это два независимых заказа Ozon внутри одного заказа Roota, с отдельными ключами идемпотентности и всеми номерами коробок. В общем случае посылок может быть больше двух из-за упаковочных правил.

Каждый этап перед созданием перепроверяет свой тариф. Если тариф вырос, создание блокируется с сообщением студии: автоматической доплаты покупателю нет. После неоднозначного результата создания повтор использует прежнее тело и ключ, не делает новый независимый заказ. Готовность к отгрузке и этикетки по-прежнему оформляются в кабинете Ozon. Предзаказ не создаётся в Ozon за несколько недель до изготовления.

Первое полученное отправление не завершает весь заказ. Обращение по возврату первой полученной части уже доступно, ждать изготовления второй не требуется. Обычная отмена с возвратом товаров в остатки после оформления этапа блокируется; полное получение вручную нельзя отметить до получения всех частей. Синхронизация старого снимка не может стереть добавленные вторым этапом коробки. Уже вручённая первая часть с полной историей не опрашивается постоянно в ожидании изготовления второй. Автоматическое пересоздание всех отменённых посылок для раздельного заказа заблокировано: нельзя незаметно объединить этапы или заново создать уже отправленную часть.

Опция относится к Ozon. Ручную Яндекс Доставку студия согласует отдельно; выбор курьера сбрасывает автоматическое разбиение Ozon.

## DaData

Добавлены последовательные поля «Город → Улица → Дом, корпус», затем отдельная квартира. Источник — [официальное API подсказок DaData](https://dadata.ru/api/suggest/address/), заявленный бесплатный лимит — 10 000 запросов в день, общий для подсказок аккаунта. Текущая карта ПВЗ Яндекса остаётся без изменений; её ключ не является ключом DaData.

Серверный маршрут `/api/address-suggestions` передаёт DaData только поисковый фрагмент города/улицы/дома и идентификаторы родителя. Квартира, телефон, имя и заказ туда не отправляются. API-ключ хранится только на сервере. Есть задержка 350 мс, отмена устаревших ответов, ограничения запросов на сеанс и общий локальный предел 9000/сутки на процесс. При нескольких процессах/общем ключе это не единая распределённая квота; бесплатный предел контролирует также сам провайдер. Платный тариф автоматически не включается.

Дом предлагается из справочника; для числового ввода исключаются несовпадающие числовые префиксы. Отсутствие варианта не является доказательством отсутствия дома: справочники неполны. Всегда доступен ручной ввод. Квартира заполняется покупателем без обещания проверки её существования. При изменении города или улицы зависимые поля и готовый адрес сбрасываются.

Владелец предоставил ключ. `DADATA_API_KEY` сохранён в исключённых из Git `.env.local` и `.env.stage.local` с правами 0600. Секретный ключ не использован и не сохранён: подсказкам он не нужен. Живыми запросами к официальному API проверены Москва по «мос», улица Яблочкова по «яблоч» и поиск домов; «454» не найден. 29.10.2026 ключ добавлен в закрытое серверное окружение действующего приложения Timeweb; секретный ключ подсказкам не передаётся. Новый договор или платная подписка от имени владельца не оформлялись.

## Порядок выпуска

1. Сохранить резервную копию и текущую ревизию. Убедиться, что предыдущие миграции проекта по упаковке, Саду и производственным задачам уже применены.
2. Применить `database/migrations/20261028_delivery_tracking_returns.sql` к прямому PostgreSQL.
3. Затем применить `database/migrations/20261028_split_dispatch.sql`. Миграции повторяемы. Они добавляют таблицы и проверки, но не делят старые заказы и не создают отправления. Права CRUD ограничены существующей ролью приложения `roota_app`; при иной роли выдать минимальные права её владельцу отдельно.
4. Убедиться, что у частного приложения Ozon есть scope `delivery-api.return` либо `delivery-api.all`. Чтение списка возвратов текущим подключением ранее проверено.
5. Добавить предоставленный `DADATA_API_KEY` в закрытое окружение production при выпуске. Локально ключ уже настроен и проверен. Убедиться, что S3 доступно и приватно; используются текущие реквизиты, новый бакет не создаётся.
6. Выпустить код с обычным worker. Проверить в изолированной среде адрес, выбор раздельной отправки, итог и персональную страницу; контрольные реальные отправления делать только по отдельному решению владельца.
7. В админке проверить первую фоновую синхронизацию возвратов и данные дат. Если таблицы ещё отсутствуют, админка объясняет необходимость миграции, форма заявки покупателю скрыта, вместо поломанного оформления.

После отдельного согласия владельца 29.10.2026 обе миграции применены одной транзакцией. Проверены права `roota_app`, защитные условия SQL-функций и неизменность сумм шести существующих заказов. Перед применением создан зашифрованный логический архив схемы и всех рабочих данных; исключено только содержимое обновляемых справочников `delivery_points` и `delivery_city_catalog`. Проверены аутентичность архива и его оглавление через `pg_restore --list`; полный восстановительный прогон не выполнялся. Сохранены прежние определения пяти изменяемых функций. Тесты используют изолированную БД и подставные API, включая потерянный ответ создания и повтор с тем же ключом. Точный физический маршрут прямой посылки по сортировочным центрам по-прежнему не заявляется.
