# Выпуск и восстановление

## Условия выпуска

Рабочая ветка — codex/roota-admin, основа — origin/main 2247829. Существующая архитектура Next.js / Vercel / Supabase сохранена. Next.js обновлён для устранения известных уязвимостей. Схему из seed.sql на существующей базе не запускать.

Владелец согласовал выпуск без отдельного облачного тестового проекта. Все сценарии с созданием заказов выполняются в PGlite и отдельном локальном PostgreSQL. На рабочем проекте проверять чтение, отказ гостю, вход владельца и публичную витрину; реальные платежи и сообщения не выполнять.

1. Зафиксировать актуальные данные, схему, функции, триггеры, политики, права и настройки buckets. Данные сохранять одним SQL-запросом для согласованного MVCC-снимка. Фотографии выгрузить с SHA-256 в каталог вне Git с правами 700/600.
2. Проверить восстановление копии локально и сохранение количества записей и остатков после миграции. Перед выпуском обновить копию, если на рабочем сайте были новые заказы или правки.
3. Выполнить проверки кода и SQL. Подготовить сборку Vercel до переключения основного адреса. Не направлять посетителей на новую сборку, пока схема не обновлена: она использует новые поля.
4. Применить по порядку `supabase/migrations/202610050001_admin.sql` и `202610050002_storage.sql`. Каждая содержит BEGIN/COMMIT. При ошибке откатить незавершённую транзакцию; не продолжать следующую миграцию.
5. Настроить окружение Vercel и пересобрать выпуск. Переключить основной адрес только на успешную сборку. Текущий rollback отключил автоматическое назначение домена; обычный push сам по себе сайт не переключает.
6. Проверить основные страницы, метаданные, robots/sitemap, 401 от гостевого GET /api/orders, редирект гостя из админки, вход владельца, прежние товары и фотографии, количество заказов и сохранённые остатки. Записать коммит, deployment URL, время и результаты.

## Переменные окружения

- NEXT_PUBLIC_SUPABASE_URL и NEXT_PUBLIC_SUPABASE_ANON_KEY: существующие публичные параметры проекта.
- SUPABASE_SERVICE_ROLE_KEY: только серверная переменная Vercel, без NEXT_PUBLIC. Не записывать в Git, сообщения или клиентские компоненты.
- ADMIN_EMAILS: согласованные два email через запятую. Пустой список закрывает доступ всем.
- NEXT_PUBLIC_SITE_URL: https://roota-liart.vercel.app до отдельного решения о домене.
- NOTIFICATIONS_ENABLED=false. TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID не нужны до согласования канала. Не включать отправку при проверках.

Supabase Auth должен содержать подтверждённые учётные записи владельцев. Пароли вводит владелец. Сервер проверяет пользователя через Auth getUser и сверяет подтверждённый email с ADMIN_EMAILS при каждом чтении закрытых данных и изменении.

## Проверки локально

`npm test` запускает транзакционные тесты PGlite. Для конкурентной проверки нужен отдельный локальный PostgreSQL, пользователь roota_test и Unix-сокет; сетевое подключение к продакшну тест не поддерживает.

`ROOTA_TEST_PG_SOCKET=/absolute/private/socket/directory npm test`

`npm run lint`, `npx tsc --noEmit --incremental false`, `npm run build`.

`node --import tsx scripts/verify-backup.mts /absolute/backup/directory` восстанавливает таблицы в изолированный PGlite, проверяет количество записей, SHA-256 файлов и отсутствие изменения остатков при миграции. Контакты в вывод не попадают. Это проверка локального восстановления; она не заменяет резервную копию Auth или всей инфраструктуры Supabase.

## Восстановление

До COMMIT ошибка SQL откатывает изменения целиком. При частично выполненном выпуске не удалять новые таблицы, колонки, файлы и заказы: они могут уже содержать новые данные. Добавленные поля совместимы со старой витриной; старый триггер списания оставлен и отличает новые транзакционные заказы по request_key.

Предпочтительный откат после успешной миграции — остановить переключение домена или вернуть последнюю проверенную защищённую сборку, сохранив новую схему, затем исправить ошибку следующей миграцией. Не возвращать открытый GET /api/orders из старой версии. Не восстанавливать старый триггер отмены поверх новой функции: это вызовет двойное возвращение остатка.

Если требуется восстановление данных, сначала создать пустую изолированную базу, восстановить исходную структуру из schema_snapshot.json (дополнения production-additions.sql фиксируют фактически найденные отличия), загрузить JSON в порядке связей с временно отключёнными пользовательскими триггерами, восстановить триггеры/права и сверить идентификаторы, связи, количества и остатки. Фотографии восстановить по прежним путям и проверить хэши. После этого переносить только подтверждённые исправления в рабочую базу.

Нельзя накрывать рабочую базу старой копией после новых продаж: отдельно согласовать и сохранить все заказы и изменения после времени снимка. Auth не изменяется миграциями и не очищается при восстановлении таблиц магазина. Два старых заказа без позиций сохраняются без выдуманного состава.

## Особенности существующей базы

- На order_items есть AFTER INSERT-триггер списания. Миграция оставляет совместимость для старого кода и пропускает списание для новых RPC-заказов, где оно выполняется внутри транзакции.
- Старые резервы с существующими позициями переносятся без изменения stock_qty; пустые заказы не получают выдуманный резерв.
- Старые restore_stock_on_cancel и sync_in_stock заменяются согласованными правилами. Отмена выполняется только через change_order, не прямым UPDATE из Table Editor.
- waitlist в рабочей базе имеет email/telegram/notified_at. Миграция сохраняет эти поля и добавляет contact для существующей формы email/телефон.
- Существующие фото в публичном products bucket остаются по прежним URL. Новые оригиналы и черновики хранятся в закрытом product-drafts. Публичные media-маршруты отдают только фото опубликованного изделия или опубликованный главный фон.
