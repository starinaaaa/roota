# Доставка Ozon

Подготовлены два варианта: доставка в ПВЗ Ozon и ручная курьерская доставка Яндексом по Москве и Подмосковью. При выборе Ozon покупатель оплачивает доставку и страховку по предварительному расчёту. Перед сохранением заказа сервер повторяет расчёт, проверяет состав корзины и итог до копейки. При сбое или неизвестной цене оформление Ozon блокируется. Курьерская ветка не зависит от расчёта Ozon и оплачивается отдельно в приложении покупателем.

Текущая инфраструктура — Timeweb PostgreSQL и App Platform; см. [протокол переноса](migration/VERIFICATION.md). Инструкции ниже о Vercel/Supabase относятся к прежней инфраструктуре и не являются командой менять текущий хостинг.

## Настройка production

В Vercel нужны серверные переменные `OZON_CLIENT_ID` и `OZON_CLIENT_SECRET`. Поддерживаются приложения с `delivery-api.all`; при отказе индивидуальных scopes сервер пробует этот вариант только в рамках выданных приложению прав. Для отдельных прав приложению Ozon нужны области доступа `delivery-api.shipment-method`, `delivery-api.delivery`, `delivery-api.delivery-point`, `delivery-api.order`, `delivery-api.posting`.

Если есть ровно один активный метод отгрузки, сервер определит его ID через `/v1/shipment-method/search`. Для нескольких методов задайте `OZON_SHIPMENT_METHOD_ID`. Адрес отправления берётся из выбранного метода в Ozon, а не из адреса покупателя. Метод должен быть активным; сейчас Ozon предусматривает самостоятельную передачу в пункт отгрузки.

Необязательная `OZON_HANDLING_DAYS` задаёт дни до передачи заказа. Для предзаказа к ней добавляется срок изготовления товара. Возвращённый Ozon `estimated_delivery_days` показывается рядом с выбранным ПВЗ и в итогах независимо от этой настройки, как ориентировочное время перевозки после передачи Ozon. При отсутствии срока показывается просьба уточнить его у студии до оплаты; произвольный срок не подставляется.

После сборки выполняется безопасная проверка подключения: в Build Logs выводятся только ID активного метода либо HTTP-статус и категория отказа OAuth, без ключей или токена. Отказ не отменяет публикацию интерфейса, но оформление остаётся заблокировано до исправления подключения.

Сначала примените миграцию `20261006065907_ozon_delivery.sql`, затем публикуйте код. В `/admin/delivery` отображается подключение и ID метода. Каталог автоматически обновляется каждый день через защищённый Vercel Cron (`CRON_SECRET`). Один запуск ограничен четырьмя минутами; прерванный обход продолжается с курсора. Кнопка «Обновить пункты выдачи» нужна только для внепланового обновления. Параллельные запуски блокируются пятиминутной арендой в БД. Недоступные карточки ПВЗ с ответом 404 изолируются и пропускаются, остальные пункты продолжают загружаться. Карта и поиск сразу получают все страницы города; список справа показывает их частями для быстрой работы. Доступность выбранного пункта для конкретного заказа проверяется через API перед оплатой.

## Упаковка

Тарелки распределяются по две в коробку и одна в остатке: 3 → 2 + 1, 4 → 2 + 2, 5 → 2 + 2 + 1. Подтверждённые параметры: одна тарелка — 600 г, две — 1000 г; обе коробки 25 × 25 × 6 см. Правила для трёх и четырёх тарелок отключены миграцией `20261023_plate_parcel_weights.sql`; другие категории по-прежнему требуют точного правила упаковки.

В расчёт Ozon передаются все посылки с отдельной объявленной стоимостью; цены доставки и страховки суммируются до копейки. Для новых расчётов плата за упаковку составляет 250 ₽ за каждую посылку: четыре тарелки в двух коробках — 500 ₽. Сохранённая цена уже оплаченного заказа не меняется. Срок — самый длинный из сроков посылок, неизвестный срок не подменяется. ПВЗ доступен только при возможности доставки каждой коробки. Снимки состава и правил сохраняются с расчётом и заказом; миграция `20261023_parcel_packing_validation.sql` проверяет актуальность каждого правила, включая остаток.

Создание передаёт покупательский `order_number` в `order_external_id`, а в `posting_external_id` — тот же номер с суффиксом коробки. Описание получает тип из категории в единственном числе с правильным родом: «Тарелка керамическая», «Стакан керамический», «Ваза керамическая». Поддерживаются slug и русское название категории (включая stakany/Стаканы); для неизвестной категории используется «Керамическое изделие». Тип не дублируется, если уже включён в название товара. Все номера отправлений сохраняются в `order_shipments.status_history.postings`; `posting_number` остаётся основным номером для совместимости. Синхронизация запрашивает все коробки, а итоговый статус достигает выдачи/получения только когда его достигли все коробки. Страницы покупателя и админки показывают все номера. Старые заказы без плана коробок сохраняют исходную упаковку и цену.

### Замена существующего отправления

Операционный скрипт `scripts/repack-paid-order.mts ORDER_UUID OLD_POSTING` по умолчанию только проверяет состояние и цену в Ozon и выводит план без контактов. Использует `TARGET_DATABASE_URL` с TLS и серверные ключи Ozon. После публикации кода добавить `--apply` для замены оплаченного заказа, ещё не переданного в доставку: сохранить план и новый ключ, отменить все старые посылки, дождаться подтверждения отмены каждой, создать новые, атомарно сохранить номера и сбросить этап доставки на подготовку. Повтор той же команды продолжает сохранённую операцию с тем же ключом и телом. Первоначальные данные и цепочка предыдущих замен сохранены в `status_history.replacement.previous`. Каждая новая замена получает свежий ключ и суффикс ревизии в идентификаторах посылок; повтор незавершённой операции использует сохранённый ключ и тело. Скрипт поддерживает одну и несколько посылок, включая уже отменённые в Ozon.

В админке оплаченного заказа с отменённой доставкой есть кнопка «Пересоздать отменённые отправления». Сервер перепроверяет, что все старые посылки отменены, и собирает новые по текущим правилам упаковки. Статусы показываются на русском. Действие доступно только администратору в рабочем окружении с включённым созданием отправлений.

Оплаченная покупателем сумма не меняется; дополнительный расход перевозчика остаётся за студией и показывается в предварительном расчёте. Скрипт не вызывает почтовые/Telegram-уведомления и не подтверждает новые отправления к отгрузке. Этикетки и готовность оформляются в Ozon после упаковки. Не применять скрипт до публикации кода: старая версия синхронизации отслеживает только основной номер и может затереть список остальных.

## Заказы и оплата

Оформление на сайте создаёт локальный неоплаченный заказ и запись доставки. Создание отправления доступно администратору только после подтверждения заказа и поступления оплаты. Для будущей Robokassa вызывайте `createPaidShipment` из доверенного обработчика после проверки подписи, суммы и подтверждения заказа. Браузерный редирект успешной оплаты не подтверждает оплату.

Ozon `/v1/order/create` не принимает флаг «оплачен»: условие оплаты проверяется в нашей системе. Ключ идемпотентности и тело первого запроса сохраняются до вызова Ozon; повтор после таймаута использует те же данные. При изменении стоимости доставки перед созданием отправления система требует согласовать разницу.

Готовность к отгрузке и этикетку пока оформляйте в кабинете Ozon. Админка сохраняет номер отправления и обновляет статус и историю. Фоновые обновления учитывают все посылки. Для операционной замены используйте описанный выше скрипт.

## Проверка

`npm test` проверяет контакты, упаковку, обработку редиректов/cookie, определение метода, точные суммы, защиту от подмены, устаревшие расчёты, транзакционный откат и идемпотентность. Тесты используют локальную PostgreSQL-совместимую базу и подставной HTTP-транспорт; не создают отправления. Отдельный тест конкурентного PostgreSQL требует `TEST_DATABASE_URL` и иначе пропускается.

Для проверки рабочего API нужны настоящие ключи и номер покупателя, зарегистрированного в Ozon. Полный тест создания реального отправления согласовывается отдельно.

## Ручная курьерская доставка

Перед публикацией выбора Яндекс Доставки примените `database/migrations/20261021_yandex_courier.sql`, затем `database/migrations/20261021_checkout_consents.sql`. Эти файлы подготовлены локально; применение к рабочей базе отложено по указанию владельца. Сигнатуры SQL-функций и права доступа сохраняются. Первая миграция добавляет отдельную ветку `yandex_courier`: обязательные Telegram и адрес, серверная проверка корзины, резерв и оплата только изделий. Доставка и страховка в платёж и чек не добавляются; запись `order_shipments` не создаётся. Вторая требует двух отметок согласия и сохраняет актуальную редакцию подписки; старые подписки не переписываются.

Контакт, адрес и способ получения доступны в карточке заказа в админке. Студия отвечает в Telegram в течение суток, вручную согласует стоимость и время, оформляет доставку до двери и передаёт заказ курьеру. Покупатель оплачивает курьера в приложении отдельно от изделий. API Яндекса не подключается.
