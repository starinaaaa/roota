> Это снимок исследования до последующих изменений. Позже владелец утвердил упаковку 250 ₽ за каждую посылку и разработку отслеживания, возвратов, раздельной отправки и DaData. Текущее состояние кода и порядок включения: [описание изменений](DELIVERY-TRACKING-RETURNS.md). Таблицы API-тарифов ниже остаются результатами исходной проверки.

Дата: **28 октября 2026 года**. Живые проверки: примерно **19:17–19:26 МСК**. Проект: Roota, https://roota.moscow. Исследована текущая рабочая копия `/Users/starina/roota`, доступная рабочая PostgreSQL и действующее подключение Ozon Delivery API.

**Границы работы:** создан только этот отчёт. Рабочий код, конфигурация, база, отправления и баланс не изменялись; миграций, сборки с postbuild, деплоя, создания, подтверждения, отмены или редактирования отправлений не было. SQL выполнялся в транзакциях `BEGIN READ ONLY` с `ROLLBACK`; прикладные функции, которые обновляют данные, не вызывались. Для API использовались только чтение и предварительный расчёт. Ключи, токены, телефоны, персональные ссылки покупателей и номера реальных отправлений здесь не приводятся.

Уровни подтверждения:

- **[API]** — получен успешный ответ действующего Ozon API в этой сессии. Предварительный расчёт не доказывает окончательную стоимость или успешность будущего создания отправления.
- **[БД]** — проверено безопасным чтением доступной рабочей базы.
- **[Код]** — установлено по текущим локальным исходникам; это не самостоятельное доказательство публикации каждой локальной правки.
- **[Док]** — подтверждено официальным документом; ссылки приведены рядом и в разделе 11.

## 1. Краткие выводы — что реально возможно

1. **Доставка курьером Ozon до двери поддерживается тем же Delivery API и рассчитывается по действующему методу «рута».** Проверены все пять направлений. Новый перевозчик или Seller API для этого не нужны. В текущем интерфейсе Roota такая ветка Ozon ещё отсутствует. **[API, Код, Док: S1, S2]**
2. **Самозанятые могут использовать сервис.** Документация прямо включает их в перечень участников. Метод «рута» активен, с самостоятельной сдачей и получением возвратов на московском ПВЗ; API принимает курьерский вариант расчёта с этим методом. Личная подписанная редакция договора Roota в кабинете отдельно не выгружалась. **[API, Док: S3, S4, Проверить]**
3. **Предположение «курьер обязательно дороже ПВЗ» не подтвердилось.** Для исследованной коробки API вернул курьерскую перевозку на **30 ₽ дешевле** во всех пяти городах. Вместе со страховкой это снижение на **16,22–19,11%**. Это снимок предварительных расчётов для конкретных координат, а не общероссийская тарифная гарантия. **[API]**
4. **Главный риск для керамики — условия фиксации повреждения и страховые исключения.** Повреждение нужно фиксировать при получении, в присутствии курьера или в ПВЗ. В типовом страховом договоре есть отдельное исключение, связанное с целой транспортировочной упаковкой. Нельзя обещать покупателю автоматическое возмещение любого боя. **[Док: S8–S10]**
5. **Автоматическое отслеживание уже реализовано и обновляет рабочие данные.** Есть статус каждой коробки, агрегированный этап заказа, история основного отправления, время синхронизации и фоновые задания. Следует расширить существующее решение, а не строить его заново. **[Код, БД, API]**
6. **Ozon уже возвращает даты доставки, которые Roota отбрасывает при валидации ответа.** На двух существующих коробках получены `original_delivery_at` и `delivery_at`; в сохранённых снимках БД этих полей нет. Это небольшая и полезная первая доработка. **[API, Код, БД]**
7. **Приоритет:** сначала полнота отслеживания, особенно ETA и возвраты; затем подготовка упаковки/инструкции получения и ограниченный запуск курьера. Массовый запуск без уточнения окончательного счёта и страховых условий не рекомендован. **[Оценка]**

## 2. Текущее состояние API-интеграции Roota

### 2.1. Стек и инфраструктура

В `package.json`: Next.js 16.3.x, React 19, TypeScript, Zod, `pg`, Better Auth, интеграция Robokassa. Текущий слой `lib/db` работает с прямым PostgreSQL. В документации переноса указаны Timeweb App Platform, PostgreSQL Timeweb и российское S3. Наличие папки `supabase` и типа `SupabaseClient` в старых интерфейсах не означает, что рабочая база по-прежнему Supabase. **[Код: `lib/db/pool.ts`, `lib/db/query.ts`, `docs/migration/VERIFICATION.md`]**

В рабочем дереве много существующих изменений и новых файлов. Они оставлены как есть. Выводы о возможностях исходников относятся именно к этой копии; работу фоновой синхронизации дополнительно подтверждают свежие записи рабочей БД. **[Код, БД]**

### 2.2. Транспорт и авторизация

[Транспорт](/Users/starina/roota/lib/delivery/ozon-transport.ts) получает токен через `POST https://xapi.ozon.ru/oauth/token`, `grant_type=client_credentials`, используя серверные `OZON_CLIENT_ID` и `OZON_CLIENT_SECRET`. Вызовы идут на `https://api-delivery.ozon.ru`, все используемые методы имеют версию `/v1/`. Это **Ozon Delivery API**, не маркетплейсный Seller API, не прежний Rocket API и не API перевозчика Ozon. **[Код, Док: S1]**

Текущие scopes: `delivery-api.shipment-method`, `.delivery`, `.delivery-point`, `.order`, `.posting`; при отказе из-за scope транспорт повторяет авторизацию с `delivery-api.all`. Токен кешируется в памяти; учтены истечение срока, сброс после 401, cookie и редиректы 302/307 testcookie, таймаут 15 секунд и запрет перехода с секретами на другой origin. Повтор исходного вызова после 401 и backoff для 429 сейчас отдельно не реализованы. **[Код]**

Локальный `.env.local` ключей Ozon не содержит. Необходимые ключи обнаружены в закрытом `.env.stage.local`; доступ к рабочей базе получен с имеющимися локальными настройками миграции. Несмотря на название файла окружения, успешные ответы сопоставлены с существующими отправлениями доступной рабочей базы и методом «рута». Значения секретов не печатались. **[API, БД]**

### 2.4. Оформление и расчёт

[Адаптер](/Users/starina/roota/lib/delivery/ozon-adapter.ts) объявляет `methods: ["point"]`. Последовательность: проверка получателя `/v1/delivery/check-client`, получение/проверка ПВЗ, `/v1/order/checkout`. Телефон должен принадлежать зарегистрированному пользователю Ozon. **[Код, Док: S1, S6]**

[Сервис расчёта](/Users/starina/roota/lib/delivery/service.ts) собирает корзину и актуальные правила упаковки на сервере, сохраняет расчёт в `delivery_quotes` на 10 минут. Цена покупателю:

`Σ estimated_delivery_cost + Σ estimated_insurance_cost + 250 ₽ за упаковку на заказ`.

250 ₽ — плата Roota, не комиссия Ozon. Суммы сводятся до копеек; неизвестная цена блокирует оформление. Срок берётся максимальный по коробкам, неизвестный срок не подменяется. На сервере перепроверяются корзина, упаковка и актуальность расчёта. **[Код]**

Одна/две тарелки распределяются по коробкам 1 или 2 штуки, большие количества — по две и одна в остатке. **Рабочая БД:** одна тарелка — **600 г, 265 × 255 × 65 мм**, две — **1000 г, те же размеры**; старые правила на 3/4 тарелки выключены. Текст `docs/OZON-DELIVERY.md` ещё упоминает 250 × 250 × 60 мм — это расхождение старого описания с рабочими правилами. Исследовательский расчёт выполнен по заданным пользователем 265 × 255 × 65 мм. **[БД, Код]**

В `postings` передаются `request_id`, `shipment_method_id`, `declared_value` в RUB, вес в граммах, стороны в миллиметрах и при наличии `cutoff_at` — плановая передача Ozon, а не желаемое время вручения. Объявленная стоимость каждой коробки равна стоимости её товаров. **[Код: `lib/delivery/postings.ts`]**

### 2.5. Создание и хранение отправлений

[Создание](/Users/starina/roota/lib/delivery/shipments.ts) разрешено только в production с `OZON_SHIPMENTS_ENABLED=true`, после оплаты и подтверждения заказа. Ветка доступна администратору; автоматический вызов создания после платежа сам по себе не следует считать включённым. До `/v1/order/create` сохраняются тело запроса и ключ идемпотентности. Повтор использует те же данные. Готовность и этикетки штатно оформляются в кабинете Ozon. **[Код]**

Payload включает `order_external_id` с номером Roota, `recipient.phone_number/full_name`, `delivery.delivery_point.delivery_point_id`, посылки с отдельными внешними ID, описаниями керамики, стоимостью и габаритами. Курьерский адрес сейчас не формируется. **[Код: `lib/delivery/shipment-payload.ts`]**

| Хранилище | Назначение |
|---|---|
| `delivery_quotes` | Срок действия, корзина, упаковка, выбранный ПВЗ, цены, метод, `cutoff_at` |
| `orders.delivery_details` | Снимок доставки и упаковки при оформлении |
| `order_shipments` | `state`, `order_number`, основной `posting_number`, `carrier_status`, `carrier_changed_at`, `status_history`, `synced_at`, `next_sync_at`, `last_error`, lease, идемпотентность и payload |
| `order_shipments.status_history.postings` | Номера и текущие статусы всех коробок |
| `order_shipments.status_history.history` | История основного отправления |
| `orders.tracking_number`, `delivery_stage` | Совместимый основной номер и этап для интерфейса |
| `order_events` | Локальные события изменения этапа/статуса заказа |

**[Код, БД]** Локальная история событий магазина не равна полной истории перемещений Ozon.

### 2.6. Уже реализовано / отсутствует

Реализованы выбор ПВЗ, реальный расчёт, страховка, несколько коробок, безопасное создание, ручное обновление статуса, фоновое пакетное обновление, агрегирование этапов и показ коробок покупателю и администратору. Есть операционное пересоздание отменённых отправлений; в исследовании оно не запускалось. **[Код]**

Отсутствуют курьерская ветка Ozon, сохранение ETA и срока хранения из `posting/info`, полноценная временная шкала каждой коробки, интеграция возвратных методов, скачивание страхового полиса, UI проблем по данным возвратов. Возможность ручной доставки Яндексом по Москве/Подмосковью — отдельная ветка, без Ozon-курьера и без автоматического API Яндекса. **[Код]**

## 3. Возможность доставки курьером до двери

### 3.1. Что подтверждено для Roota

**Да, можно сдать на текущем ПВЗ в Москве и доставить курьером получателю.** Во всех успешных расчётах использован один и тот же действующий `shipment_method_id` метода «рута» с `dropoff`; менялась только конечная точка. Официальная схема работы также разделяет самостоятельную отгрузку и конечную доставку. **[API, Док: S1, S5]**

Самозанятость не является общим запретом сервиса. Курьерский расчёт с имеющимся ключом и методом принят API. Однако исследование не создавало отправления и не проверяло заключённый Roota договор построчно: это подтверждение доступности расчёта, а не юридическая гарантия любых маршрутов. **[API, Док: S3, S4, Проверить]**

### 3.2. Параметры API

Для предварительной цены `/v1/order/checkout` вместо ПВЗ передаётся:

```json
{
  "delivery": {
    "courier": {
      "coordinates": { "latitude": 55.752429, "longitude": 37.453341 }
    }
  }
}
```

Телефон, список коробок, объявленная стоимость и метод сохраняются. Для расчёта документация требует **координаты**, не полный почтовый адрес. Это же тело успешно проверено запросом. **[API, Док: S1]**

Для будущего `/v1/order/create` у `delivery.courier` схема содержит:

| Поле | Требование схемы |
|---|---|
| `coordinates.latitude`, `.longitude` | Обязательно |
| `zip_code`, `country`, `region`, `city`, `street` | Обязательно |
| `house_number` | Nullable; в интерфейсе Roota разумно требовать дом для обычного адреса |
| `entrance`, `floor`, `apartment`, `intercom` | Необязательные строки/nullable |

Также нужны телефон и данные получателя по схеме заказа. Отдельных полей даты/интервала вручения, корпуса или комментария в раскрытой схеме `courier` не обнаружено. Корпус/строение нужно корректно нормализовать в адресе и подтвердить формат с Ozon. Не следует придумывать параметры `delivery_date`, `timeslot`, `leave_at_door` или пересылать целый адрес одной строкой вместо документированных полей. **[Док: S2, Проверить]**

### 3.3. Дата, время и география

Покупатель может выбрать дату курьерского вручения **в приложении Ozon**, открыв заказ. Документированного метода получения/бронирования интервалов через этот Delivery API не найдено. В Roota нужно показывать срок и пояснение о выборе даты в Ozon; обещать выбор интервала непосредственно до оплаты пока нельзя. **[Док: S6; Проверить для точных временных окон и переноса]**

География — РФ, получатели — физлица с аккаунтом Ozon. Пять исследованных адресов курьерский расчёт прошли; это не подтверждает покрытие всех адресов даже в этих городах. Случайно попавшая в предварительную выборку станица Дербентская Краснодарского края дала `delivery_point_not_found` для курьера; из сравнения Краснодар→город она исключена и заменена городским адресом. Это наглядно показывает необходимость проверки конкретных координат, а не списка «поддерживаемых городов». **[API, Док: S3]**

Обычные товары и КГТ обслуживаются разными методами. В справке КГТ определяется весом от 35 до 125 кг, длинной стороной от 200 см либо объёмом от 500 л, с отдельными предельными размерами. У «рута» `is_bulky=false`; исследованная посылка далеко от этих границ. У проверенных ПВЗ API вернул `max_weight_g=35000`, `max_price=500000 RUB` и стороны до 5000 мм. Последние значения — ответ конкретного справочника, **не универсальная гарантия приёма пятиметровой коробки и не лимиты курьерской доставки**. Итоговую совместимость проверять checkout и ограничениями отгрузочного/конечного пункта. **[API, Док: S5]**

Максимальная объявленная стоимость по публичному описанию бизнеса — 500 000 ₽ на отправление; действующий страховой сертификат может задавать дополнительные условия. Исследуемые 6000 ₽ проходят. **[API, Док: S6, S10]**

### 3.4. Керамика

Керамика прямо перечислена в разделе **«Хрупкие товары»** требований упаковки FBS, на которые ссылается инструкция отгрузки Ozon Доставки для бизнеса. Следовательно, общего запрета на обычную керамическую посуду нет. Требуются соответствующая коробка, амортизирующая упаковка и маркировка. Для Roota рекомендуется прочная трёхслойная коробка, не менее двух слоёв пузырчатой плёнки, фиксация и заполнение пустот; упаковка должна исключать контакт двух тарелок и движение внутри. Рекомендация усилить защиту не меняет тарифные размеры без фактического перемера. **[Док: S7, S11; Оценка]**

Хрупкость в текущем API-payload не выделена специальным флагом. Описание «керамическая тарелка» и наклейка не являются обещанием специальной ручной перевозки. Число перегрузок и отдельный бережный режим API не гарантируют. Уникальная авторская вещь не становится автоматически музейным/антикварным предметом, но исключения для конкретных дорогих или коллекционных изделий следует сверить с договором до отправки. **[Код, Проверить]**

## 5. Минусы и риски для авторской керамики

| Ситуация | ПВЗ | Курьер до двери | Значение для Roota / подтверждение |

| Перевозка | Магистральная логистика и точка выдачи | Магистральная логистика и доставка по адресу | Число перегрузок и статистика боя не опубликованы в изученных источниках. Дополнительный последний этап не доказывает больший процент повреждений. **[Проверить, Оценка]** |

**Наиболее существенный страховой риск:** типовой договор исключает случаи без фиксации дефекта при выдаче, нарушения упаковки и содержит формулировку об исключении при целой транспортировочной упаковке. Для тарелки, способной разбиться внутри внешне целой коробки, это принципиально. Страховая сумма по шаблону — объявленная стоимость, максимум 500 000 ₽; дополнительно расходы логистики могут покрываться до 20 000 ₽ в пределах фактически оплаченного. Это условия шаблона, не проверка личного полиса Roota. **[Док: S10, Проверить]**

КИД предусматривает уведомление незамедлительно, не позднее 30 рабочих дней, требование через кабинет, фото и акт Ozon; рассмотрение — 10 рабочих дней после последнего документа, выплата — 3 рабочих дня после решения. Курьерское вручение упомянуто в требованиях фиксации. Отдельной гарантии более простого спора для ПВЗ нет. **[Док: S9]**

Практический порядок для Roota **[Оценка на основе S8–S10]**:

1. Снимать состояние изделий и непрерывное видео упаковки с читаемой этикеткой; хранить связь материалов с коробкой.
2. До вручения сообщить покупателю: проверить коробку и тарелку при получении, при повреждении зафиксировать дефект вместе с курьером/сотрудником, отказаться от проблемного отправления и сразу написать Roota.
3. Сохранить упаковку, фотографии, видео, подтверждение цены и доступный акт; открыть спор по заказу/возврату в кабинете.
4. Отдельно решить вопрос с покупателем; ждать выплату перевозчика как условие начала рассмотрения обращения покупателя не следует.
5. По отменам контролировать прибытие возврата. В инструкции бизнеса размещение оплачивается со второго дня, после 10 дней возврат утилизируется. Этот риск действует для обоих способов вручения. **[Док: S13]**

Задержка доставки сама по себе не является страховым случаем по КИД. Статистика повреждений, гарантированное время на осмотр у курьера, форма акта при внешне целой коробке и оплата повторной попытки требуют письменного уточнения. **[Док: S9; Проверить]**

### 6.4. Что мешает текущей реализации

[Схема ответа](/Users/starina/roota/lib/delivery/posting-status.ts) оставляет только `posting_number`, `status`, `status_changed_at`. Zod удаляет остальные поля, поэтому ETA и `storage_expires_at` не доходят до записи в БД. Это **ограничение Roota**, а не Ozon. **[Код, API, БД]**

[Фоновая синхронизация](/Users/starina/roota/lib/delivery/shipment-sync.ts) опрашивает текущие статусы всех коробок пакетами по 100, но историю получает только по основному номеру. Запрос истории запускается при изменении **общего** статуса или отсутствии истории. Движение одной коробки может не изменить общий статус, поэтому историю каждой коробки так восстановить нельзя. Ошибка получения истории при наличии старой истории может ожидать нового общего статуса или ручного обновления. **[Код]**

Планировщик `scripts/worker.mjs`, запускаемый через `scripts/start.mjs` при `JOBS_ENABLED=true`, обращается к `/api/cron/order-shipments` раз в 15 минут. Задание защищено `CRON_SECRET`; БД выдаёт lease для 20 заказов и защищает параллельную обработку. Функция применения статуса обновляет локальный этап и события; завершённые/отменённые заказы исключаются из дальнейшего прямого опроса. Поэтому без отдельного возвратного цикла дальнейшая судьба отменённой посылки не отслеживается. **[Код]**

Админка уже показывает текущий статус, номера, время синхронизации и `last_error`. Персональная страница `/order/[token]` показывает общий этап, состав коробок и их статусы, время обновления. Полной временной шкалы и ETA там сейчас нет. Текст этапа «В пути» ориентирован на ПВЗ; для Ozon-курьера его потребуется адаптировать. **[Код]**

Чтение требует bearer-токен частного приложения; scopes документированы по группам. Для возвратов предусмотрен `delivery-api.return`, для всего API — `delivery-api.all`. ## 8. Предлагаемая архитектура изменений

Это проект решения, **не выполненные изменения**.

### A. Курьерская доставка при оформлении

**[Оценка на основе существующего кода и S1–S2]** Сохранить нынешний блок доставки. Внутри Ozon добавить два варианта: «В пункт выдачи» и «Курьером до двери». Отдельную существующую Яндекс-ветку оставить с явным названием перевозчика, чтобы не смешивать оплату и сроки.

При ПВЗ остаётся текущая карта. При курьере — город, улица и дом с адресными подсказками, подтверждение точки на карте, квартира/подъезд/этаж/домофон, телефон. Почтовый индекс и регион получать из нормализованного адреса с возможностью проверки. Геокодер выбирать после проверки условий/стоимости; существующее отображение карты не доказывает доступность бесплатного геокодинга.

Перед оплатой показать одну понятную итоговую сумму доставки, включающую страховку и действующую плату упаковки; в деталях можно раскрыть составляющие. Ориентировочный срок обозначать как срок перевозки, отдельно от изготовления. Подпись: дату вручения покупатель выбирает в Ozon после появления отправления. Не показывать неподтверждённый календарь временных слотов.

Технически:

1. Расширить модель адресата доставки дискриминированным вариантом `point | courier`, адаптер — поддержкой courier. У внутренней модели может быть своё поле `kind`, но в Ozon отправлять только документированное тело.
2. Для курьера сохранять адрес и координаты в серверном расчёте. Привязать его к корзине, телефону, коробкам, методу и дате сдачи; TTL оставить 10 минут. Изменение дома/точки обнуляет расчёт.
3. Перед оплатой пересчитать на сервере; не доверять цене и координатам из одного лишь браузерного запроса без проверки адресного соответствия. При недоступности маршрута не подставлять ноль или цену ПВЗ.
4. Обобщить `shipmentPayload` и проверки создания: сейчас они рассчитывают на `details.point.id`. Новый вариант должен проходить весь путь quote → заказ → оплата → создание, включая повтор/идемпотентность и возможную замену.
5. Сохранять адресный снимок в `orders.delivery_details` и в неизменном payload. Не менять адрес уже оплаченного/созданного отправления скрыто.
6. Обновить ограничения SQL, типы, условия согласий, описание доставки в письмах и чеке, админку, страницу заказа и страницу подтверждения. Проверить реальные определения рабочих функций перед проектированием миграции.
7. Запускать под отдельной серверной настройкой, с возможностью выключить только Ozon-курьера при сбое. Создание проверять сначала по контрактным фикстурам; реальное контрольное отправление требует отдельного согласования.

### B. Отслеживание

**[Оценка]** Использовать текущий worker и PostgreSQL. Новая очередь, брокер событий, отдельный сервер и миграция на другой хостинг не нужны.

Минимальная доработка: расширить allowlist схемы `posting/info` нужными nullable-полями, сохранять ETA и срок хранения по каждой коробке в существующем JSON, показывать их в админке и на уже существующей защищённой ссылке заказа. Показывать «Обновлено …», при ошибке — последнее достоверное состояние и признак устаревших данных. Не раскрывать покупателю сырые внутренние ошибки, payload, телефон и страховые документы.

Для надёжной полной истории позже целесообразна отдельная таблица `delivery_postings` с уникальным `(provider, posting_number)` и таблица событий с уникальным `(provider, posting_number, flow, status, occurred_at)`. Это снимет зависимость от основного номера и смешения `history`/`postings`/операционной замены в одном JSON. Миграция должна быть аддитивной, с совместимостью старых заказов; сейчас не выполнялась.

Возвраты — отдельный поток жизненного цикла, не «продолжать posting/info после canceled». Читать список по методу, сопоставлять номера, сохранять `cancellation_reason/responsible`, дату/место получения, сроки и состояние. Уведомлять студию о необходимости забрать возврат. Не превращать отмену доставки в автоматическую отмену оплаченной покупки или возврат денег.

### Polling и экономия запросов

- Сохранить пакетный `posting/info` до 100 номеров и существующие leases. Увеличивать размер claim только после оценки времени и нагрузки; при 20 заказах за проход текущая пропускная способность — около 80 заказов в час, фактически меньше/больше зависит от коробок и повторов. При росте будет накапливаться очередь.
- Историю запрашивать для **изменившейся конкретной коробки**, а также при её отсутствии/неудаче, отдельно хранить попытку и успех получения истории. Удаление избыточных запросов не должно приводить к потере событий второй коробки.
- Период 15 минут оставить для «у курьера», «в ПВЗ», ожидаемого вручения и проблем. Для дальнего `on_way` допустимы 1–3 часа, для долгой подготовки — 3–6 часов. Это выбор Roota, не требование Ozon; после внедрения адаптивности worker может продолжать будить задание каждые 15 минут, а БД выбирать только due-записи.
- На 429 учитывать `Retry-After`, если есть; иначе экспоненциальный backoff с jitter. На 401 обновить токен и один раз повторить чтение; на 403 остановить бесполезные повторы и показать администратору проблему прав.
- Успешно вручённые посылки исключать из прямого polling; отменённые передавать возвратному циклу. Отсутствие истории повторять ограниченно независимо от общего статуса.
- Открытие страницы покупателя должно читать сохранённый снимок, без запроса к Ozon на каждую загрузку. Для ручного «Обновить» — серверный cooldown и объединение одновременных запросов.
- Ссылку заказа считать секретом доступа: проверка 64-символьного токена, `noindex`, `no-referrer`, приватное кеширование, защита от перебора и отсутствие токенов в аналитике. Часть этих мер уже существует в `lib/order-access.ts` и странице заказа; аудит логов и всех путей доступа нужен перед расширением.

Webhooks стоит рассматривать только после получения официального контракта, правил подписи, повторов и доступа. Даже при их появлении нужен редкий контрольный polling для пропущенных событий. **[Оценка, Проверить]**

## 9. Сложность внедрения и расходы

Оценки для знакомого с проектом разработчика, с проверкой в изолированной среде. Это не коммерческое предложение. Этапы частично пересекаются; общую сумму часов нельзя получить простым сложением всех строк.

| Работа | Оценка |
|---|---|
| Сохранение и показ ETA/срока хранения на существующей базе | 0,5–1,5 рабочего дня |
| История каждой коробки, повтор после ошибок, простая временная шкала | 1–2 дня |
| Возвратный цикл, причины, уведомления о заборе | 1–3 дня |
| Ozon-курьер: модель, адрес, quote, создание, SQL, админка, письма | 3–6 дней |
| Проверка оплаты, нескольких коробок, ошибок и регрессий | 1–2 дня, с пересечением предыдущих работ |
| Новые нормализованные таблицы посылок и событий | Дополнительно 1–3 дня при выборе этой архитектуры |

**[Оценка]** Разумный небольшой выпуск отслеживания — примерно 1–3 дня; полноценные отслеживание/возвраты/курьер — ориентировочно 6–12 рабочих дней, плюс ожидание ответов Ozon и отдельно согласованной контрольной отправки.

По API в просмотренной документации отдельная цена чтения/расчёта не указана; это не доказательство отсутствия тарифа в индивидуальных условиях. Дополнительный постоянный сервер не требуется. Возможные расходы — адресные подсказки/геокодинг, небольшой рост БД/логов, хранение фото и видео упаковки, поддержка клиентов, обратная доставка и повторные попытки. Точную цену инфраструктуры без проверки текущего тарифа Timeweb и выбранного геокодера оценивать в рублях нельзя. **[Док, Оценка, Проверить]**

Пример запросов **[Оценка]**: 20 активных однокоробочных заказов, все due каждые 15 минут, помещаются в один `posting/info`: **96 запросов в сутки**, а не 1920. Плюс история только при изменениях, редкая сверка возвратов, авторизация и ручные действия. В худшем случае первые/изменившиеся состояния добавят по запросу истории на коробку. При 200 заказах и нынешнем claim=20 всем уже нельзя обещать свежесть 15 минут — требуется увеличить производительность и адаптивность расписания.

Экономический выбор курьера оценивать по **суммарному расходу**, а не только транспортной строке: `цена перевозчика + страховка + упаковка + ожидаемые потери/возвраты + время студии`. Разница 30 ₽ по тарифу мала относительно 6000 ₽ за тарелку: даже небольшой рост невозмещённого боя или неудачных вручений может её перекрыть. Процент боя и вероятность неуспеха не измерены; числовой прогноз убытка не приводится. **[API, Оценка]**

## 10. Пошаговый план с приоритетами

1. **P0, без реализации:** получить ответ Ozon на вопросы раздела 12, сопоставить личный договор/полис Roota с шаблоном, уточнить покрытие боя при целой коробке и процедуру акта у курьера. Повторить quote к дате будущей передачи: тарифные изменения объявлены с 30 октября.
2. **P1, первый согласованный выпуск:** сохранять и показывать ETA и свежесть данных, полную историю всех коробок; исправить повтор запроса истории и обозначение проблем. Добавить тесты на nullable ETA, неизвестный статус, раздельное прибытие/получение коробок и недоступный API.
3. **P1:** возвратный polling и предупреждение студии о прибытии возврата/сроке забора. Это полезно даже при сохранении только ПВЗ.
4. **P2:** согласовать упаковку, инструкции проверки и материалы для претензии; уточнить повторный выезд, перенос и запрет/возможность оставления у двери.
5. **P2, после разрешения на код:** реализовать courier quote и адрес, серверные проверки/SQL и весь жизненный цикл заказа. Проверить без реальных отправлений через контрактные фикстуры и изолированную БД.
6. **P2, отдельное разрешение:** одна контрольная отправка с оплачиваемой логистикой и согласным получателем, осмотром при курьере, сверкой окончательного счёта и ETA. В текущем исследовании не выполнялась.
7. **P3:** небольшой пилот на подтверждённых адресах и неделимых коробках, измерение стоимости, сроков, неудачных попыток и обращений. Расширять после фактических данных, сохранив ПВЗ как альтернативу.

### Итоговая рекомендация

**Доставку до двери стоит добавить как выбор после небольшого пилота**, если покупатель готов получать и проверять посылку лично. Техническая доступность по методу «рута» и пяти адресам подтверждена. По текущим предварительным расчётам она **не дороже, а на 30 ₽ дешевле ПВЗ**; постоянную разницу и окончательные расходы подтвердит только сверка условий и счёта после разрешённого пилота.

Для Roota наиболее существенны бой внутри целой коробки, фиксация дефекта при курьере, отсутствие покупателя и расходы на возврат; авторскую вещь невозможно полностью заменить одной страховой выплатой. ПВЗ остаётся полезным вариантом для людей, которым удобнее самостоятельно выбрать момент получения.

**Автоматическое отслеживание можно расширять уже сейчас: основа уже работает. Первым выпуском рекомендованы ETA, история каждой коробки и контроль возвратов.** Это даст пользу всем Ozon-заказам и закроет риск пропустить возврат до утилизации. Курьер — следующий согласованный этап; рабочая реализация в рамках этого исследования не начиналась.
