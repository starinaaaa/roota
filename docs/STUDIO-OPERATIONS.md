# Возвраты и воронка — 15 октября 2026

Изменения расширяют существующие Next.js, Supabase и Robokassa; новых зависимостей нет.

## UniSender

Проверены проекты Orders `8374546` и Marketing `8374550`, соответствие локальных ключей и активные webhook `/api/email/unisender`. Служебные `order_*` идут через SERVICE; подписки и напоминания — через MARKETING. Одинаковые проектные ключи блокируют отправку. Маркетинговая отписка отменяет добровольные письма, сохраняя служебные; hard bounce и жалоба продолжают блокировать оба канала. Поздняя отписка больше не ослабляет более строгую блокировку. Проверки выполняются на тестовой базе; письмо реальному покупателю для проверки не отправляется.

## Возвраты

В карточке рабочего заказа — причина, заметки, получение изделия, полный возврат Robokassa и проверка статуса. Нужен серверный `ROBOKASSA_PASSWORD3`, отдельный от платёжных паролей. Сумма и фискальные позиции берутся из сохранённого платежа, включая доставку; пользователь не вводит произвольную сумму. API запрашивает именно полную исходную сумму: частичные возвраты пока оформляются в кабинете. Перед отправкой сверяются OpStateExt, сумма и оплаченный рабочий режим. Тестовые/неоплаченные платежи исключены.

Атомарный захват блокирует повтор; тайм-аут сохраняет unknown/sending, автоматического повторения нет. Принятая заявка — processing, деньги считаются возвращёнными только после GetState finished с совпавшими ID и суммой. Обновление статуса выполняется кнопкой владельца. Возврат из кабинета можно связать по ID после явной ручной сверки заказа: GetState сам не возвращает исходный invoice. Сверка записывается с ID владельца в историю.

Возврат денег не отменяет заказ и не пополняет склад. Неотправленный заказ отменяется существующим действием освобождения резерва. Полученное изделие после осмотра возвращается на склад через существующий редактор товара. История покупателя показывает до 50 последних заказов по существующей customer_id, статусы, суммы и заметки; покупатели не объединяются по приблизительному совпадению контактов.

## Воронка

`/admin/analytics`: витрина → добавление в корзину → оформление → созданный заказ → подтверждённая оплата. Считаются уникальные сессии корзины (существующая cookie до 30 дней), прошедшие этапы по порядку. Источник — первые utm_source/utm_medium/utm_campaign, закреплённые при просмотре. Проценты — от предыдущего этапа; источники показывают конверсию из просмотра в оплату. Периоды 7/30/90 дней. События создания заказа и оплаты записываются триггерами, повтор callback не увеличивает счётчик, sandbox не учитывается. Прежние заказы не восстанавливают отсутствующие просмотры.

Хранятся хэш сессии, допустимый путь витрины, ограниченные UTM, этап, служебный ID заказа и время; query string, токены заказа, контакты, IP и сырые ошибки не собираются. Ошибки оформления и платёжной формы содержат только фиксированные категории. До 300 событий в сутки на сессию, дедупликация просмотров в течение минуты; срок хранения 90 дней, очистка ограниченными порциями при новых событиях. Блокировка JavaScript и боты влияют на полноту данных. Полного отличения человека от бота нет.

## Выпуск

Применить `20261015105811_studio_returns_funnel.sql` перед публикацией приложения. Таблицы и функции закрыты для anon/authenticated; каждое действие студии отдельно проверяет администратора. Миграция добавляет структуры и триггеры, не меняет прежние заказы и остатки. Проверки: PGlite, npm test, TypeScript, ESLint, production build. Настоящий денежный возврат выполняет владелец после сверки заказа; проверки кода его не инициируют.
