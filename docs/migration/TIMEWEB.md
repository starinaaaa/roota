# Перенос Roota в Timeweb

Статус: код и сценарии подготовлены; рабочий домен не переключён. Перед переключением заполнить протокол проверки ниже. Исходный Supabase не удалять.

## Подтверждённый объём

Исходный код: main `21e147f`, проверен с origin 15.10.2026. Рабочая ветка — `codex/timeweb-postgres-migration`.

Повторный аудит обнаружил 35 прикладных таблиц, 54 функции (одна управляет облачным расписанием), три бакета и четыре задания cron. Снимок `database/schema.sql` взят из фактического каталога, включая определения, отсутствующие в истории миграций. В нём сохранены ограничения, триггеры и бизнес-функции, удалена функция управления Supabase Vault/pg_net/cron, функции выполняются с правами вызывающего пользователя. Политики облачного Data API не переносятся: доступ к SQL есть только у сервера.

По последнему указанию владельца переносить только четыре изделия из `database/migration-selection.json`: Колыбельный, Солнышко, Невидимка, Поцелуй. На момент аудита все опубликованы, остаток каждого — 10, активных резервов по ним нет. Остальные изделия и их файлы остаются в исходной системе и полной резервной копии.

Выборочный экспорт сохраняет нужную категорию, фотографии, редиректы, опубликованное содержимое и его черновик, подходящие правила упаковки, шаблоны и безопасные настройки писем, справочник доставки. `featuredIds` фильтруется по выбранным изделиям. Состояние загрузки/блокировки справочника начинается заново.

Не переносятся клиенты, корзины, позиции корзин, заказы и позиции, платежи и их JSON/чеки, расчёты доставки с телефонами, отправления и их запросы, возвраты, отзывы и фото покупателей, токены доступа, события заказов, заявки/подписки, черновики оформления, письма/блокировки/очереди, события поступления, сессии и события воронки. Экспорт останавливается при новой таблице/колонке/непроверенной зависимости или изменении исходных функций. Контакты тестовых покупателей проверяются также внутри переносимых текстов и JSON. Адрес магазина `hello@roota.moscow` разрешён как публичный служебный контакт.

## Безопасное окружение

`.env.migration.local` — локальный файл с правами 0600, исключён из Git. Пароли не помещать в команды командной строки, сообщения, отчёты или скриншоты. В App Platform официальный CA передаётся через `DATABASE_CA_BASE64`, если недоступен файл `DATABASE_CA_FILE`. TLS проверяет сертификат и имя сервера; отключение проверки сертификатов не предусмотрено.

Исходный IPv6-адрес Supabase недоступен в текущей сети. Для разового экспорта используется сессионное IPv4-соединение 5432 с официальным CA Supabase. Это не зависимость новой рабочей версии. Новая версия использует прямой `DATABASE_URL` Timeweb, один пул на процесс, по умолчанию 4 соединения, ограничение 1–8, таймаут соединения 5 секунд и SQL 15 секунд. Короткие задания аналитики имеют отдельный дедлайн и освобождают соединения при отмене.

Доступ к S3 выполняется AWS SDK на сервере. В одном приватном бакете сохраняются пространства `products/`, `product-drafts/`, `review-photos/`. Витрина отдаёт только опубликованные изображения по прежним `/media/...` и `/site-media/...`; просмотр черновиков требует входа и короткой подписанной ссылки. Скопированные объекты проверяются чтением и SHA-256. Неподписанный HTTP-запрос к проверочному объекту должен быть запрещён.

Supabase JS оставлен только как инструмент исходного резервирования и интерфейс типов на этапе сборки; исполняемый код приложения не вызывает облачный SDK. Старые Supabase Edge Functions остаются в репозитории для отката, но новая версия уведомлений обращается к Telegram с сервера напрямую.

## Последовательность

1. `npm run migration:backup -- /absolute/private/new-backup-dir` создаёт полный логический `pg_dump` и копии всех объектов, зашифрованные AES-256-GCM. Ключ `BACKUP_ENCRYPTION_KEY` хранить отдельно от копии, с защищённым дубликатом. Копия содержит тестовые персональные данные и секреты старой инфраструктуры; это не публичный артефакт.
2. Настроить `RESTORE_DATABASE_URL` на пустую локальную БД, имя заканчивается `_restore`. `npm run migration:restore-drill -- /absolute/private/backup-dir`. Восстанавливаются public и проверяются все файлы. Полное восстановление управляемой платформы Auth/Vault/Storage в независимую Supabase-инсталляцию этим тестом не подтверждается; исходная платформа остаётся для отката.
3. После восстановления можно добавить `EXPORT_FROM_RESTORE=true`: экспорт прочитает тот же проверенный снимок локально, сверив идентификатор архива с закрытым служебным маркером в восстановленной БД. Это исключает повторную передачу большого справочника из Supabase. Порции читаются по первичному ключу, без повторного обхода предыдущих строк. `MIGRATION_STOCK_POLICY=preserve` для четырёх выбранных тарелок. `npm run migration:export -- /absolute/private/new-export-dir /absolute/private/backup-dir` делает один REPEATABLE READ READ ONLY снимок. Без отметки успешного восстановления экспорт не запускается. Номер следующего счёта Robokassa сохраняется выше всех исходных номеров, хотя сами платежи не импортируются.
4. `npm run migration:import -- /absolute/private/export-dir` допускает только пустую назначенную проверочную БД. Создание схемы, импорт, ограничения и сверка пустых таблиц выполняются в одной транзакции. Триггеры отключаются только на время загрузки каталога и восстанавливаются до COMMIT. Никакие INSERT-триггеры не должны создавать письма или события аналитики при импорте.
Для медленного соединения используйте `MIGRATION_COMPRESSED_IMPORT=true`: локальный проверочный PostgreSQL с pgcrypto упаковывает порции в сжатые зашифрованные PGP-пакеты, Timeweb распаковывает их внутри транзакции. Для этого в пустой целевой БД временно устанавливается доверенное pgcrypto в отдельной схеме; расширение и служебная схема удаляются до COMMIT. Существующее расширение скрипт не удаляет и в таком случае отказывает. Это средство разового переноса, не зависимость рабочего приложения. Проверены обычный и сжатый импорт на локальном PostgreSQL. [Описание стандартных функций PostgreSQL](https://www.postgresql.org/docs/current/pgcrypto.html).

5. `npm run migration:storage -- /absolute/private/export-dir /absolute/private/backup-dir` копирует только связанные изображения, оригиналы и готовые варианты размеров. Отзывы покупателей и посторонние объекты остаются в резервной копии. Несовпадающий существующий объект не перезаписывается.
6. Better Auth: таблицы созданы из схемы библиотеки 1.7.9. Публичная регистрация отключена; доступ проверяет подтверждённый email из `ADMIN_EMAILS`, сессии хранятся в PostgreSQL, cookie HttpOnly/SameSite, срок 8 часов, ограничение попыток в БД. Начальную учётную запись создаёт `scripts/migration/admin.ts` из локальных `ADMIN_BOOTSTRAP_EMAIL/PASSWORD`; существующий аккаунт скрипт не перезаписывает. После создания удалить bootstrap-пароль из окружения.
7. Для рабочей версии назначить отдельного пользователя БД, не владельца объектов, через управление Timeweb. `scripts/migration/permissions.ts` требует владельца с CREATEROLE; стандартный `gen_user` этого права не имеет. Не наделять сервер приложения CREATEROLE/SUPERUSER/BYPASSRLS. Минимальные разрешения перечислены в скрипте. Провести вход и операции под фактической рабочей ролью.
8. Запустить отдельно с `APP_ENV=migration`, `ROBOKASSA_MODE=test`, без live-паролей/Password3, `OZON_SHIPMENTS_ENABLED=false`, уведомления и почту сначала отключить. Не создавать реальные списания или отправления. Проверить браузерный путь и подписанное тестовое уведомление. SQL-проверки дополнительно моделируют реальные резервы и конкуренцию без вызова внешних финансовых API.
9. Включить и проверить резервирование Timeweb, фактический срок хранения и восстановление в отдельную БД. Подтвердить регион и доступ к копиям. Для объектов определить версионирование/отдельную копию и стоимость хранения до включения платных параметров. Наличие кода резервирования не означает, что ежедневные копии уже настроены.

## Фоновые задания

`JOBS_ENABLED=true` запускает лёгкий `scripts/worker.mjs` рядом с Next через `npm start`. Запросы идут на 127.0.0.1 с `CRON_SECRET`: обслуживание резервов/старых корзин каждую минуту, почта каждую минуту при включённом канале, статусы отправлений каждые 15 минут, справочник ПВЗ в 02:00 UTC. Повторные задачи защищены существующими транзакционными захватами и арендой в БД; внутри процесса повтор одного незавершённого запроса блокируется. Перезапуск процесса возобновляет периодические задачи. Для более строгого SLA нужен внешний российский планировщик и мониторинг пропущенных запусков; отдельно согласовать его стоимость, если потребуется ресурс.

Старые pg_cron/pg_net задания Supabase отключить только в момент успешного переключения, сохранив точные определения для отката. Не оставлять старый и новый планировщики одновременно направленными в новую рабочую базу.

## Кеш и режим оплаты

Общий кеш содержит только публичные DTO каталога и опубликованное содержимое, TTL 60 секунд, теги `catalog`/`site`. Изменение товара/публикация инвалидируют соответствующий тег. Транзакционное оформление всегда заново проверяет актуальную цену и остаток. Персональные корзины, заказы, письма и админка не входят в общий кеш и возвращают private/no-store.

Страница доставки теперь показывает режим из той же серверной настройки, что создаёт оплату. Рабочий режим дополнительно требует `APP_ENV=production`, `ROBOKASSA_LIVE_ENABLED=true`, `ROBOKASSA_SMZ_READY=true`. Создание отправлений требует отдельного `OZON_SHIPMENTS_ENABLED=true`. В проверочном окружении запрос возврата денег блокируется.

Географию неподтверждённых логов/копий нельзя считать установленной по доменному имени API.

## Протокол и переключение

Зафиксировать результаты в `docs/migration/VERIFICATION.md`. До переключения проверить: вход/выход и запрет постороннего входа; четыре изделия и каждое фото/размер; черновик сайта и публикацию с обновлением кеша; корзину с исполнением JavaScript; выбор ПВЗ/расчёт; повтор оформления; тестовую оплату/подпись/повтор callback; резерв и отмену; почту и Telegram в согласованный тестовый канал; последовательные события page_view → add_to_cart → checkout_started → order_created → paid; отсутствие live-списаний/отправлений; чистую рабочую БД после проверки.

Перед переключением: сохранить текущую ревизию приложения, безопасный снимок окружения вне Git, определения cron, DNS и копии новой базы/объектов. Кратко остановить оформление на старой версии, проверить, что реальных новых заказов нет, повторить финальный выборочный снимок. Развернуть проверенную ревизию, назначить домен только после smoke-проверки. Непроверенный выпуск не отправлять в main с автоматическим деплоем.

Откат до первых рабочих заказов: закрыть оформление на новой версии, вернуть прежний выпуск/его окружение и прежние расписания, затем открыть оформление. Новую БД и S3 сохранить для разбора. После появления рабочих заказов откат с потерей новых записей запрещён: сначала остановить запись, сохранить дельту и согласовать её перенос. Слепое восстановление старого дампа поверх новых продаж не применяется.
